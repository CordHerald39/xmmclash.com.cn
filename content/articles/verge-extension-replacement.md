## 修改前先判断数据类型

在 YAML 扩展里写一份列表，不一定表示向旧列表追加。Clash Verge Rev 官方扩展文档区分以下情况：

| 写入类型 | 预期行为 |
| --- | --- |
| 列表，如 `rules` | 写出的列表整体替换原列表 |
| 普通值，如 `tcp-concurrent` | 覆盖该值 |
| 普通嵌套对象 | 按子字段合并，未写的子字段可保留 |
| 特殊处理的字段 | 按对应版本文档核对，不能一概当作递归合并 |

这意味着将一个旧列表复制少了一部分，再放入扩展，并不会自动补回遗漏项。保存前先确定你的目标是替换、局部修改还是追加；需要对现有对象做条件处理时，脚本通常更容易表达。

## 全局扩展与订阅扩展的顺序

截至 2026-10-04 查阅的官方文档，处理链路为：订阅原文、应用设置、全局扩展配置、全局扩展脚本、订阅扩展配置、订阅扩展脚本，最后由应用回写接管字段。

因此，一个订阅扩展能影响前面全局扩展的结果，但应用接管的选项仍应在设置页面核对。不要仅凭扩展编辑器内能保存，就认定某个设置已作用于运行内核。

官方文档还明确列出 v2.5.5 起部分 DNS 和 hosts 合并行为发生变化。本文不提供跨版本通用的全字段模板；遇到这些字段时，应先核对当前版本的完整说明。

## 用一个普通值验证入口

先备份当前订阅及扩展内容。右键目标配置卡片，选择编辑扩展，确认正在编辑的是该订阅扩展而非全局扩展。可以仅对普通值做验证，例如：

```yaml
tcp-concurrent: false
```

该片段只用于确认改动入口和最终值，不代表性能优化建议。保存、重新应用配置后，查看最终配置中该项是否符合预期。对比修改前后，确认没有顺带替换其他列表。

如原值已经为 false，这次操作不会形成有意义的行为差异。应记录最终配置核对结果，而不是声称“明显提速”。具体观察是否需要重新建立连接，应结合测试对象判断。

## 列表被覆盖后的恢复步骤

1. 保留当前扩展副本，暂时停用本次改动，重新应用原配置。
2. 确认原列表恢复，判断覆盖发生在全局还是当前订阅的扩展层。
3. 如需整表替换，补齐所需内容并核对名称引用；如只需追加，改用能读取现有列表的脚本或客户端对应编辑功能。
4. 再次应用后核对最终配置，而不是只比较订阅原文。

不要改服务方原文来抵消每次扩展产生的覆盖；那会增加后续更新的维护成本。脚本按订阅条件生效的例子见[扩展脚本作用域](/articles/verge-script-scope/)。
